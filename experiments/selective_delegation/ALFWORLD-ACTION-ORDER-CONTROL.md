# Conditional ALFWorld action-order control

Prospective CPU design only; no GPU acceptance or implementation. The pending fixed
checkpoint readout remains the priority. Do not run this unless its completed result
shows a competence gain worth interpreting.

## What the current interface exposes

The pinned TextWorld PDDL environment constructs admissible commands using
`sorted(set(_valid_commands))`. Our bridge copies that native list unchanged; the
demangler runs with `shuffle=False`. The indexed public prompt enumerates this order
from zero, and the strict parser executes exactly the selected command. The training
preparer likewise copies the native list and supervises its expert command's current
index. Thus alphabetical action/argument regularities are shared by training and
evaluation. No experimental permutation has yet tested order robustness.

Sources: `alfworld_bridge.py`, `alfworld_closed_loop.py` functions `prompts` and
`parse_output`, and `alfworld_train_sft_data.py` functions `flat_prompt` and
`collect_game`. Native sorting is at the pinned ALF environment's
`textworld/envs/pddl/pddl.py:102` (also present in `envs/tw.py:102`).

## Smallest first screen: same-state command invariance

If training helps, first qualify presentation sensitivity with **96 new calls**,
without running new environment episodes: take the frozen 035 flat contexts at
call indices 0 and 4 for every one of the 12 games, seed 2026092195, with no correctness
filter. All these slots exist. For each of the resulting 24 states, evaluate base and
the fixed trained checkpoint under original and permuted command order. Preserve the
original public feedback, initial goal, history, prompt instruction, saved per-call
seed, temperature .5, top-p 1, top-k 0 and 128-token cap. Both models see both orders;
do not permute only the trained actor. Generate both original and permuted responses
fresh, rather than comparing a fresh condition to an unmatched old model call.

Use a deterministic per-game ordering: sort command strings by
SHA256(`alf-order-2026092207:` + frozen game-content SHA256 + `:` + command).
This fixes a command priority for a game, independent of outcomes, so revisiting an
unchanged command set preserves its order. Renumber contiguously and map each returned
index back to that exact native command. Only the order/index association changes;
command availability, public information and native state remain identical. Record
both lists, permutation, raw index, resolved command, prompt IDs, tokens and latency.
Reject invalid JSON/out-of-range indices without repair.

Primary descriptive quantities: semantic-command agreement across order within each
model; protocol validity; old numeric-index retention when that index now names a
different command; and the trained-minus-base change in order sensitivity. Preserve
all 24 state pairs, clustered by their 12 games/four scenes. Identical numbers are not
evidence of semantic consistency. Conversely, different commands can both be useful:
this screen tests interface invariance, **not task progress**, and should not assign
new success labels or treat an expert's single action as the only correct action.
It uses exposed states generated by the old base policy, not an on-policy trained
state distribution or fresh confirmation. No persistent goals or hidden state enter.

Expected cost is a few model minutes for 96 short replies;
an eventual GPU decision should set a 10-minute cap and check a real reply promptly.
This estimate is not a measured trained-actor throughput claim.

## Progress comparison only if warranted

The smallest end-to-end extension remains the memo's **48 new episodes**: both base
and trained flat actors on the same 12 games × two seeds, with the same deterministic
per-game permutations and unchanged 50-action/2,048-output-token/128-per-call budgets.
Compare their training effect to the completed unpermuted base/trained effect, reporting
the training-by-order interaction in native win rate, game bootstrap and four-scene
sensitivity, protocol errors, loops, actions and actual costs. All 48 slots remain
planned, with missing distinct from observed failure. This would still be an adaptive
exposed-panel control, not a new confirmatory benchmark. Wait for actual trained-actor
timing before accepting a duration; the earlier 30–60-minute estimate is provisional.

A large trained-specific order sensitivity would motivate order-varied training
examples before attributing improvement to planning. Stable gains under permutation
would weaken a simple list-position explanation but would not prove semantic
generalization: lexical matching, recipe-like task routines and shared-scene familiarity
remain possible. If 042 shows no useful training gain, stop rather than add this control.

## Selected old errors: hypotheses, not frequencies

These are post hoc examples from complete035 receipts, not a sampled prevalence audit:

- Game01, seed2195, flat calls001–005 repeatedly select index22 of23, `use desklamp 1`,
  even after feedback says the lamp is on. The command is last alphabetically. Both
  repeated-position preference and an unresolved semantic subgoal could explain this;
  the unchanged order cannot distinguish them.
- Game10, seed2195, manager worker call003 selects index18 of19,
  `take soapbottle 1 from cabinet 1`, although the task asks for soapbars. This is also
  a last-list command, but soapbottle/soapbar confusion is a competing explanation.
  Later worker calls select indices2,3 and0, so this example does not support a
  universal last-position rule.
- In the same game, successful flat call001 selects index17 of21,
  `take soapbar 1 from countertop 1`, while call003 selects the last index17 of18 to
  place it. Last-position selections can be correct, and success requires a sequence
  of changing commands, not avoiding a particular numerical index.
