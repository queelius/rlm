# Prospective TextCraft flat-action SFT: a small competence control

Status: CPU inputs prepared; **no GPU training accepted**. Activate only after the
044 flat/recursive pilot's complete readout shows a useful basic-crafting failure to
address. This is practice on public crafting actions, not training recursion or a new
hierarchical method. The separate training-control memo remains authoritative about
separating model competence from inference-time scaffolding.

## Frozen demonstrations

Source 047 freezes 32 official TRAIN tasks: 11 at annotated depth 2, 11 at depth 3, 10 at
depth 4, taking first SHA256(`2026092206:` + task ID) within each stratum. All official
VAL task IDs and root target items, plus the known eight-task pilot inventory, are
excluded before selection. The existing official split already satisfies these
exclusions: 300/288/288 eligible TRAIN tasks at depths 2/3/4. All 32 identities were saved
in `SELECTION.json` before native replay; no success filter changed the selection.

All 32 replay successfully within the fixed budget. There are 30 unique root items.
Root overlap with official VAL is zero, but **all 30 TRAIN roots occur as VAL
intermediates**, and all 126 unique crafted items appear somewhere in VAL gold traces.
This is compositional task reuse in the same synthetic recipe world—not unseen recipes
or independent facts. The split distinction is root-goal/task identity only.

The trusted gold action sequence supplies teacher supervision. Before every craft,
the teacher explicitly asks public `get_info` for that product and observes the exact
native reply. A final `{"action":"finish","message":"done"}` is included, applied,
and checked by the native evaluator. Craft `output_count` uses the actual gold
`result_count`, not the requested root quantity or a presumed repetition count.
Public initial target quantities remain exactly the 044 interface; no additional
host-derived target quantities are inserted into prompts.

The prompt is exactly 043/044 `public_prompt`: goal, root targets, initial/current
inventory, flat depth 0/maxdepth 0, remaining global calls/output tokens, and prior
actions with actual public feedback. No task ID, gold future trajectory, difficulty,
host score, hidden recipe table, or future native reply enters the prompt. Teacher
action choice is privileged supervision; it is not a claim that these actions were
generated by an informed model. In particular, the oracle selects which intermediate
to query. There is no model-code execution; the bridge runs only pinned trusted
native methods, not the full Platoon/IPython lifecycle.

## Size and masking audit

- 366 action rows: 167 `get_info`, 167 `craft`, 32 `finish`.
- 414,754 prompt tokens and 8,821 supervised action/EOS tokens; 423,575 tokens per pass.
- 3–35 rows per task; maximum prompt 3,295 tokens and action 54 tokens including EOS.
- Maximum prompt plus full 256-token generation allowance 3,551, below 8,192.
- Exact 044 limits: 96 total calls, 8,192 total emitted tokens, 256 per call; no truncation.
- Every prompt token has label −100. Only strict action JSON and the actual native EOS
  token are supervised. Feedback and all host metadata are not target tokens.

All 366 saved rows were independently reconstructed from native frame/public history,
tokenized, mask-checked and replayed to explicit successful finish. Three focused
sealed fixtures pass in 5.34 seconds: label-blind selection/root exclusions; real native
batch-size/public-history/JSON+EOS masking; and a capped trajectory retained as failed.
Ruff passes. The preparer preserves a trace for every initially selected task. Only
complete, within-budget, native-successful trajectories are training-eligible; this
is an explicit supervised-data eligibility filter, not a reported policy success
rate. Here all 32 are eligible, so no selected task was dropped or replaced.

### Declared depth is not remaining execution depth

An additive CPU audit covers all 32 selected TRAIN tasks and all eight frozen pilot
VAL tasks. It tracks ingredient units along the supplied gold trajectory: initial
stock has depth zero; each craft's outputs have depth one plus the deepest consumed
unit; shallower available units are consumed first. The final target quantity includes
the required net addition above initial stock. Query and finish actions do not add
crafting depth. This is a constructive causal chain under an explicit allocation,
not a proof of the shortest necessary plan or a replacement benchmark label.

Declared and constructive depths differ on 7/32 TRAIN and 3/8 pilot tasks. Two
declared-depth-2 TRAIN examples need only one craft plus query/finish. Thus the
11/11/10 annotation balance does not mean 11/11/10 distinct remaining chain lengths,
nor does annotation depth establish depth generalization. In these particular 40
tasks all initial items are native base items; shorter constructive chains therefore
are not evidence that pre-stocked crafted intermediates made the task easier.
The recipe graph/gold route can skip nominal levels. The audit supports inventory
pruning generally but does not causally attribute every discrepancy to initial stock.

The complete 40-row mapping and input/source hashes are preserved in
`analysis-textcraft-depth-001.json` and `.md` in the research store, generated by
`audit_textcraft_depth.py`. One small independent fixture verifies that an initially
available intermediate reduces the constructive chain without changing declared
depth. No frozen selection, demonstration, or live source was changed.

## Smallest actionable training option, conditional on044

If 044 shows basic execution/quantity/finish failures, propose **one fixed epoch** from
the unchanged base 4B, a fresh rank 8/alpha 16/dropout 0 LoRA, AdamW learning rate 1e−4,
weight decay 0, microbatch 1 and effective batch 16. That is 23 updates (22×16 rows plus
14), 8,821 supervised tokens, not an open-ended tuning campaign. Reuse the existing
audited action-SFT loss/checkpoint machinery with a new explicit TextCraft input
contract; do not import the ALF-specific row-count assumptions. Use a fixed shuffle,
BF16 base/FP32 adapter, non-reentrant gradient checkpointing and an atomic optimizer/
RNG checkpoint each update. No trainer is implemented by this CPU preparation.

A one-A100 run should be small (rough planning estimate 5–15 minutes, cap 30 minutes);
memory/runtime have not been measured for this task. Fix its terminal one-epoch
checkpoint before any VAL readout, not the best held-out step. First compare trained
versus base through the **same flat interface**, then evaluate that same checkpoint
recursively only if the competence result merits it. Flat demonstrations do not teach
delegation, child contexts, or recursive quantity planning; recursive instruction
transfer can fail independently of useful flat learning. Later full-task versus
subtask training requires a separately matched data/update/token control.

Do not train this merely because the inputs replay: if 044 already solves these tasks
or failures are explained by an interface defect, resolve that decision instead.
No failed demonstration is silently repaired, no VAL performance guides selection,
and no additional training dose is implied by preparing this option.
